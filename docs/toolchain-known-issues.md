# Pinned toolchain observations

The supported compiler is Zig 0.17.0; the issues below were reproduced on 0.15.2 and are kept for reference. The following is a locally reproduced compiler/backend issue, not a change to framework error identities or native callback ownership. No global LLVM override or toolchain upgrade is required by this workaround.

## Windows Debug uses the self-hosted backend

Zig 0.17.0 defaults to LLVM for Windows (COFF) Debug artifacts, while Linux Debug already uses the self-hosted x86_64 backend. On the 4-core Windows runner a cold `zig build test` took 1277 s with LLVM and 770 s with the self-hosted backend, so `build.zig` now selects the self-hosted backend for every Windows Debug compile step that does not pin `use_llvm`. Release builds keep LLVM, and `-Dwindows-llvm=true` restores LLVM for Debug.

The self-hosted COFF linker needs four workarounds, all applied only to those steps:

- mingw-w64 implements `_assert` as a wrapper around the UCRT export renamed through `NAME_EXPORTAS` (`__msvcrt_assert == _assert`), which the linker reports as `TODO handle name_type NAME_EXPORTAS`. Executables and tests get `src/c/windows/assert_shim.c`, which prints the CRT message and aborts. Each gets a private copy of its root module for it, because root modules are also shared with object files that are linked into the same executables.
- The mingw-w64 definition names `UIAutomationCore.DLL`, and the linker rejects the upper-case extension. `src/c/windows/uiautomationcore.def` lowers the name; `zig dlltool` turns it into the import library.
- With libc linked, the calls that `@sin`, `@cos`, `@exp`, `@log` and similar lower to are bound to the UCRT imports rather than compiler-rt's weak definitions (LLVM builds import none of them). UCRT differs in the last bit for some inputs, such as sin(-pi/4), which broke pixel-exact SVG marker tests. `src/c/windows/math` compiles compiler-rt's own transcendental code, copied from the Zig installation at build time, into a static library with strong `sin`/`cos`/`tan`/`exp`/`exp2`/`log`/`log2`/`log10` definitions and their `f` variants. Correctly rounded functions such as `sqrt`, `floor` and `fma` still come from UCRT.
- The linker drops resource sections, both from the `.rc` file a module adds and from COFF objects, so executables lost their icons, version information and manifest (and with it common controls 6, DPI awareness and the supported-OS list). `build.zig` takes the resource file off the executable, compiles it with `zig rc /:output-format coff`, and `tools/pe_resources.zig` copies the linked image with a `.rsrc` section and resource directory added. Installs and run steps use that copy.

The self-hosted backend writes no PDB, so installs skip it and panics print no stack trace (`(empty stack trace)`). To debug a Windows-only crash, rebuild with `-Dwindows-llvm=true`.

## Linux x86 Debug optional-error comparison

A main-thread diagnostic sink receives `Diagnostic` by value and compares its `err: ?anyerror` with a stored `?anyerror`. In the observed Linux x86_64 Debug code generated by the self-hosted backend, this expression can reject identical error payloads:

```zig
value.err == state.expected and value.err != null
```

The original hidden-window fixture logged `error.LayersRequired` for both values. Inspection of its preserved executable at the comparison showed the actual and expected payloads both equal to 156 (`0x009c`). The generated equality also loaded two unwritten stack bytes as optional-presence flags; in that execution those bytes differed (`0x00` and `0x7a`). The subsequent `err != null` used the correct zero-payload check. This explains why adding unrelated numeric diagnostic logging could change the failure without changing either error.

`tools/optional_error_probe.zig` is an independent reproducer using only the diagnostic value type, an explicit sink and caller-owned state. It creates no window, GUI runtime, worker or framework App. It is deliberately excluded from normal build/test targets. On the checked Linux x86_64 Zig 0.15.2 installation:

```sh
zig run -fno-llvm --dep diagnostics \
  -Mroot=tools/optional_error_probe.zig -Mdiagnostics=src/diagnostics.zig
# exits 1: comparison rejected actual=error.Example, expected=error.Example

zig run -fllvm --dep diagnostics \
  -Mroot=tools/optional_error_probe.zig -Mdiagnostics=src/diagnostics.zig
# exits 0: optional error comparison matched payloads
```

The full original fixture was preserved under the local ignored cache for inspection. Reproducer and LLVM runs establish this narrow backend pattern; they do not claim that every optional comparison or every Debug target is affected.

Native test sinks avoid the expression by explicitly unwrapping both optionals and comparing the actual `anyerror` payloads:

```zig
const matches = if (value.err) |actual|
    if (state.expected) |wanted| actual == wanted else false
else false;
```

These sinks require a non-null expected error, so either null correctly rejects the diagnostic. A sink that permits two null errors must handle that null/null case explicitly. The workaround preserves error identity checks; it never substitutes error-name strings or accepts unexpected diagnostics. Project inspection found the risky two-optional pattern in native test sinks; production diagnostic storage used null checks or unwrapped payloads. Keep that distinction when adding or reviewing future comparisons.

## Writing to `std.Io.Reader.ending`

In Zig 0.15.2, `std.http.Client.Response.reader` returns `std.Io.Reader.ending` for methods whose responses carry no body (`HEAD`, `PUT`, `TRACE`). That pointer is `@constCast` of a constant `Reader`. Methods that move its position, such as `discardRemaining` (which assigns `seek = end` before asking the stream), write to that constant. LLVM places it in read-only memory, so the write faults: on Windows Debug, and in every Linux build that uses LLVM, including ReleaseSafe. The Linux x86_64 Debug self-hosted backend keeps it writable, which is why Linux Debug runs passed:

```zig
const r = std.Io.Reader.ending;
_ = r.discardRemaining() catch 0;
// zig run -fllvm: Segmentation fault in Reader.discardRemaining
// zig run -fno-llvm: returns 0
```

This is a standard library defect, not a framework HTTP client one. Never call a position-changing `Reader` method on `Response.reader` for those methods. To read such a response's body, use `response.request.reader.bodyReader(...)`, as `src/net/fetch.zig` and the error path of `tools/s3.zig` do. On a connection that is not kept alive, return without reading. The CLI tests are built with LLVM so CI covers this path.
