# 设计原则

## 一个内核，两种内容

应用首先是窗口、事件和业务状态。内容可以由 Zig 绘制，也可以由系统 WebView 呈现。模块依赖决定成本：核心不导入内容模块，两个内容模块也不互相导入。

共享的是语义与生命周期，不是所有渲染细节。窗口标题、关闭、线程、任务队列只有一套规则；文本布局、GPU 资源和页面加载分别属于内容模块。

## 显式成本

分配器从调用者传入。异步任务明确交接上下文，队列容量明确，满队列返回错误。关闭后的窗口不能恢复。WebView 的初始化是异步状态，`ready` 之前发消息会返回 `NotReady`。

便利 API 应当组合这些规则，不应掩盖等待、分配、线程切换或失败。Zig 可以直接调用系统 ABI；需要适配复杂原生接口时，允许局部 C ABI 胶水，由 Zig 工具链统一构建。

## 状态只有一个所有者

应用持有业务状态。输入事件产生动作，动作更新状态，然后使窗口失效；绘制是当前状态的投影。连续动作无需等待重绘，因此不会因重绘合并而丢失。

控件 ID 表示跨帧身份，与绘制次序或对象地址无关。页面消息表达业务请求；后续类型化 IPC 由编译期 Zig 类型生成协议与客户端，不引入运行时反射。

## 线程规则简单可见

App 在进程主线程创建并运行。窗口、内容以及所有 UI 回调只在该线程访问。后台工作使用应用自行管理的线程，通过 `App.post` 返回结果。

框架不把每个方法包装成可能阻塞的隐式线程跳转。UI 线程不等待依赖 UI 回调的工作，也不为了伪同步接口嵌套运行事件循环。

## 性能以不做无用工作为起点

空闲时等待原生事件；重绘请求由系统合并。复用窗口绘制资源，交互路径避免堆分配。需要动画时再引入明确的时钟与截止时间，动画结束后取消唤醒。

GPU、缓存和批处理应由测量推动。二进制小、绘制快、启动快、内存低是不同指标，分别记录。目标和已测结果必须分开。

## 扩展顺序由应用能力决定

先把生命周期、输入、文本、可访问性与失败路径建立完整，再扩充控件和工具链。核心保持小而稳定；文件、数据库、更新、网络服务和开发服务器作为按需模块加入。
